# Where SWI ships, equipment slots and Default Loadouts live in the game files

Research for issue #3 (child of the wayfinder map, #1). Date: 2026-11-16.

**Primary source:** the local X4 8.00 install at
`/mnt/e/SteamLibrary/steamapps/common/X4 Foundations - 8.00`, with SWI
`starwarsmod_m1` ("Star Wars 0.9.1 HF", `version="091"`, `date="2025-12-24"`,
`<dependency version="800"/>`) and `starwars_rsp` (Reaper's Ship Pack, `version="208"`,
which depends on `SW Interworlds` `version="091"`). I unpacked the archives myself and checked
the md5 of every file I extracted against its `.cat` line.

**Secondary sources** (Egosoft's own wiki):
[Tags and flags](https://wiki.egosoft.com/X4%20Foundations%20Wiki/Modding%20Support/Assets%20Modding/Guides/Tags%20and%20flags)
and
[Breaking Changes](https://wiki.egosoft.com/X4%20Foundations%20Wiki/Modding%20Support/Breaking%20Changes).

Archive paths below are written as `<extension>/<archive> → <path inside archive>`.

## TL;DR

| Question | Answer |
|---|---|
| Ship definition | 3 layers: **ware** (`libraries/wares.xml`, `tags="ship"`, `<component ref="…_macro">`), then **macro** (`assets/units/size_*/macros/<x>_macro.xml`: stats, software, storage), then **component** (`assets/units/size_*/<x>.xml`: geometry plus all **connections**, which are the slots). `index/macros.xml` and `index/components.xml` map names to files. |
| Slots | `<connection>` elements in the ship *component* whose `tags` include `weapon`, `turret`, `shield`, `engine` (and so on). Capital ships put turret and shield slots into named `group`s. |
| Matching | An equipment component has exactly one connection tagged `component`. All of its *other* tags must appear in the slot's tags (Egosoft calls this "OTHERALL from the slot side"). SWI relies on custom tags (`xwing`, `kx7`, `isd`, `astromech`, …) to lock equipment to particular hulls. |
| Default Loadouts | **Mostly not in files.** The shipyard's presets (Empty / Low / Medium / High) are *generated by the engine* (`GenerateShipLoadout2(…, level)` with levels 0, 0.1, 0.5, 1.0). NPC ships also get engine-generated loadouts from a `level`. `libraries/loadouts.xml` holds only **15** hand-written SWI/RSP loadouts, all for game starts and scripted events. |
| Buildable | The ship ware survives SWI's patches, has `tags="ship"`, and has an `<owner faction>` that runs a shipyard or wharf. Tags such as `noplayerbuild`, `missiononly`, `blueprintsaleonly`, `limited` exclude it. After patching there are **291** ship wares; **257** are "clean and owned by a shipyard/wharf faction". |
| Consumables and software | Missiles: ship macro `<storage missile=…>`, plus launcher `<ammunition tags>` matched against missile `<missile tags>`. Drones: `<storage unit=…>`. Countermeasures and deployables: per-class capacity in `libraries/defaults.xml` (SWI patches this). Software: ship macro `<software>` list (`default="1"` / `compatible="1"`). Thrusters: a *virtual* slot matched through the ship macro's `<thruster tags="small">`. |
| Base-game data still needed | Yes. Thrusters, software, drones, mines, satellites, countermeasures and some missiles survive from base X4 and the DLCs. The pipeline must layer **base + DLCs + SWI + RSP**. It cannot read SWI alone. |

## 1. Where SWI's data files are

- `starwarsmod_m1/ext_02.cat` holds all of SWI's `libraries/*.xml` (61 files), `md/`, `aiscripts/` and `t/`.
- `starwarsmod_m1/ext_01.cat` (an 18 GB `.dat`) holds `index/macros.xml`, `index/components.xml` and every `assets/**` XML: ship components and macros, plus equipment components and macros. Extracting only `*.xml` from it gives 3,012 files.
- `starwarsmod_m1/subst_0{1,2,3}.cat` are *substitution* archives. They replace base files (UI `.xpl` scripts, loading screens, voice) and hold no ship data. One file matters for this question: they replace `ui/addons/ego_detailmonitor/menu_ship_configuration.xpl`. That is the shipyard menu, as plain Lua with kuertee UI-extension hooks added.
- `starwars_rsp/ext_01.cat` follows the same layout: `index/`, `libraries/{wares,ships,shipgroups,loadouts,jobs}.xml`, `assets/units/**`.
- Every SWI/RSP `libraries/*.xml` and `index/*.xml` is an **XML diff patch** (`<diff><add|replace|remove sel="…">`), not a whole file. They have to be applied on top of base and DLC files (issue #2 covers patch layering). I applied base `wares.xml` → 7 DLC `wares.xml` → SWI → RSP with a small RFC 5261-subset patcher. All 2,526 operations applied and none failed.
- Traps:
  - SWI ships stray copies under `libraries/backup/` and `libraries/!backup/` (for example `backup/ships.xml`, `!backup/wares.xml`), and also `md/temp`, `t/tmp`. I *infer* the engine ignores them because it loads fixed file names, so the pipeline should ignore them too.
  - Some archive paths contain spaces (`libraries/backup/charactergroups backup.xml`), so a `.cat` line has to be split from the right.
  - Index `value`s use backslashes and mixed case (`extensions\starwarsmod_m1\assets\props\WeaponSystems\…`), while archive paths differ in case (`shield_R2_s_standard_01_mk1.xml`). Path resolution must be case-insensitive.

## 2. How a ship is defined (example: T-65B X-wing)

**Ware:** `starwarsmod_m1/ext_02 → libraries/wares.xml`, inside an `<add sel="//wares">` block:

```xml
<ware id="t65b_xwing" name="{999840,100610}" description="{999840,100630}" group="ships_sw" transport="ship" volume="1" tags="ship">
  <price min="…" average="…" max="…" />
  <production time="220" amount="1" method="default"> … energycells / hullparts … </production>
  <component ref="t65b_xwing_macro" amount="1" />
  <restriction licence="generaluseship" />
  <owner faction="rebelalliance" /> <owner faction="incom" /> <owner faction="hapes" />
</ware>
```

**Macro:** `ext_01 → assets/units/size_s/macros/t65b_xwing_macro.xml`, found through `index/macros.xml`. It holds:

- `class="ship_s"`, which gives the size class;
- `<component ref="t65b_xwing"/>`;
- `identification` text IDs, `hull max="8500"`, `physics` (mass, drag, inertia), `jerk`, `steeringcurve`, `purpose`, `people capacity`;
- `<storage missile="6"/>`;
- `<thruster tags=" small "/>`;
- a `<software>` list;
- `<connections>` for *fixed* internals (cockpit, cargo `storage_container_300_macro`, docking).

**Component:** `ext_01 → assets/units/size_s/t65b_xwing.xml`, found through `index/components.xml`. It has about 1,400 lines of geometry. The slots are `<connection>`s:

```xml
<connection name="con_weapon_01" tags=" weapon small platformcollision kx5 kx7 kx10 tie7 tie1 symmetry_1 symmetry_right" parent="wing_b">
<connection name="con_weapon_05" tags="component weapon small krupx ">   <!-- missile launcher -->
<connection name="con_shield_01" tags="small shield unhittable ">
<connection name="con_shield_03" tags="shield astromech ">              <!-- the R2 unit -->
<connection name="con_engine_01" tags="engine small xwing " parent="wing_b">  <!-- ×4 -->
```

Other notes:

- Display names are text IDs on page `999840`, which is SWI's page in `t/0001*.xml`.
- `group="ships_sw"` on the ware is SWI's own ware group.
- Ship-side data is spread over three files. **Stats** come from the macro and **slots** from the component. Ware data (price, owners, licence) lives only in `wares.xml`.
- `libraries/ships.xml` and `shipgroups.xml` (SWI *replaces* `//ships` and `//groups` entirely, with 475 `<ship>` entries) are **NPC spawn roles**, not buildable ships. Example: `rebelalliance_fighter_xwing_s` → group → `<select macro="t65b_xwing_macro"/>`. The builder doesn't need them.
- 310 ship macros live under SWI/RSP `assets/units/size_*/macros`. **35 have no ware**: menu backdrops (`*_menu_macro`), test hulls (`test_light_bulb_macro`, `lambda_shuttle_test_macro`) and spawn-only hulls. So the ship list must come from **wares**, not from the macro index.

## 3. Slots, and how equipment is matched to a slot

- **Slots** are `<connection>`s in the ship component whose tags contain an equipment-type tag (`weapon`, `turret`, `shield`, `engine`). Size comes from `small`, `medium`, `large` or `extralarge`. Flags such as `hittable`/`unhittable`, `platformcollision`, `symmetry_*`, `noshield`/`noturret` sit alongside. See the wiki's [Tags and flags](https://wiki.egosoft.com/X4%20Foundations%20Wiki/Modding%20Support/Assets%20Modding/Guides/Tags%20and%20flags).
- **Groups:** L and XL slots carry `group="…"`. The ISD-I (`size_xl/isd_1.xml`, 232 connections) has groups such as `left-front-pd` (`turret small llaser red green hittable`), `left-niche-front` (`turret medium xx9dual nk7 green hittable`) and `group_mid_left` (`turret large htbdual green red hittable`). Each group mixes turret slots and `medium shield hittable standard` slots. Engines sit in `enginegroup` (`engine extralarge isd`), and two ship-level shields are tagged `isd shield component`. The game equips a group as one unit (one turret macro × N, one shield macro), and loadouts address groups by name (see §4).
- **Equipment side:** the equipment's component has one connection tagged `component`; per the wiki, "other tags in this connection define the compatibility". Examples:
  - `weapon_kx7_s_laser.xml` → `WeaponCon_01 tags="component weapon kx7 small"`
  - `engine_xwing.xml` → `EngineConnection01 tags="engine xwing small"`
  - `shield_R2_s_standard_01_mk1.xml` → `tags="shield astromech"`
  - `shield_s_inv_standard.xml` (used by `shield_s_novaldex45_macro`) → `tags="component shield small"`
- **Rule:** drop `component` from the equipment's tags; every remaining tag must be present on the slot. The wiki names this mode **OTHERALL** and says "all ship upgrades will use OTHERALL from the slot side". I tested the rule against every equipment entry in SWI's and RSP's 15 library loadouts: **123 match, 4 mismatch, 2 unresolved** (a base-game engine I didn't extract). Example mismatch: `sw_warlord_int` puts `weapon_ls1_s_laser_macro` (tag `tie1`) on the TIE Interceptor, whose slots are `weapon small tie7 ms1 ms2`. SWI's hand-written loadouts are therefore **not reliable** as a source of truth, and the app should validate them.
- SWI hulls are locked to SWI equipment through custom tags. X4 6.00 made engine and shield slots refuse equipment unless they share a tag such as `standard` (see [Breaking Changes](https://wiki.egosoft.com/X4%20Foundations%20Wiki/Modding%20Support/Breaking%20Changes)). SWI instead uses tags like `xwing`, `isd`, `kx7`, `astromech`, so in practice equipment is matched by hull or family, not just by size.
- **Equipment wares** (post-patch): engines 121 SWI + 19 base, shields 80 + 21, weapons 69 + 20, turrets 203 + 10, missiles 18 + 21, thrusters 18 (all base), software 12 (base). The base-game survivors are mostly Xenon/Kha'ak/Split items. Each ware points to its macro (`<component ref="weapon_kx7_s_laser_macro"/>`), and the macro points to its component.

## 4. Where Default Loadouts are defined

- **The in-game shipyard presets are generated, not stored.** In `menu_ship_configuration.xpl`/`.lua` (both base and SWI's substituted copy):
  - `menu.getPresetLoadouts()` inserts `empty` (preset 0), `low` (0.1), `medium` (0.5) and `high` (1.0).
  - Applying one calls `Helper.getLoadoutHelper2(C.GenerateShipLoadout2, …, preset)`. That is an engine (C/FFI) function, `GenerateShipLoadout2(UILoadout2*, containerid, shipid, macroname, float level)`.
  - Its algorithm is not in any data file. It depends on the selling station's available equipment (`containerid`).
- **NPC ships** use the same generator. SWI `libraries/jobs.xml` has 869 `<loadout>` blocks with `<level exact="1"/>`, `<level min="0.7" max="1.0"/>` and similar. `libraries/loadoutrules.xml` only sets **units (drones) and deployables** per ruleset (SWI replaces the `default` rulesets for both).
- **`libraries/loadouts.xml`** (base: 50; SWI: 13 added; RSP: 2) holds explicit, named loadouts. Each SWI and RSP one is referenced only by game starts or scripted events (`md/setup_gamestarts_sw.xml`, `setup_gamestarts_showcase.xml`, `setup_event_*`, `gs_scientist.xml`). Example: `sw_xwing_mc80start` for `t65b_xwing_macro`. Format:
  - `<macros>`: `<engine|weapon|shield macro=… path="../con_x"/>`
  - `<groups>`: `<turrets|shields macro=… path=".." group="left-dualtb" exact="4"/>`
  - `<ammunition>`: missiles, countermeasures, and drones as `<unit>`, each with `exact`
  - `<software>`: `<software ware=…/>`
  - `<virtualmacros>`: `<thruster macro=…/>`
- `C.GetLoadoutsInfo` also lists named loadouts in the menu. Its `deleteable` field suggests these are mostly the player's own saved loadouts. I did not confirm whether library loadouts appear there.
- **Consequence for the Glossary's "Default Loadout":** for almost every buildable SWI ship there is **no stored default loadout**. The options are:
  - (a) reimplement or approximate the engine's level-based generator;
  - (b) offer only the 15 library loadouts where they exist;
  - (c) define a builder-side default, such as "first compatible equipment per slot".

  This decision belongs to the map.

## 5. What makes a ship buildable in SWI

- SWI `wares.xml` operations: about 930 `<remove sel="…ware[@id=…]">` (base ships and equipment are deleted), 131 adds, plus many replaces of names, prices and production. After patching there are **291** ware entries with `tags="ship"`. 275 point to SWI/RSP macros; 16 are base Xenon/Kha'ak/drone hulls.
- Signals I found in the data:
  1. **The ware exists** after patching, with `tags` containing `ship`.
  2. **Exclusion tags:**
     - `noplayerbuild` (SWI uses it for `*_dummyware` entries such as `venator_01_dummyware`);
     - `missiononly`, `blueprintsaleonly`, `limited` (the Executor, `mc80_homeone`, `subjugator_class`);
     - `noblueprint`/`noplayerblueprint` (these block building at the player's own wharf).
  3. **An owner that sells:** the ware's `<owner faction>`s must include a faction that runs a shipyard or wharf. In SWI `god.xml` (which replaces `/god`), shipyards are stations with `<select … tags="[shipyard]"/>`. Shipyard owners: anoat, ascendancy, commerceguild, corporate, galempire, hapes, hoersh, huttcartel, kamino, kuat, mandodw, moncal, newrepublic, rendili, sienar, sith, transgalmeg. Wharves add bountyhunters, corellia, incom, miningguild, naboo, rebelalliance.
  4. `<restriction licence>` (`generaluseship`, `capitalship`, …) only limits who may *buy*, not whether the ship exists.
- Result: 257 ship wares are owned by a shipyard/wharf faction and carry no exclusion tag; 14 are owned but tagged; 20 have no selling owner (Xenon, Kha'ak, `player`, `ownerless`, `blacksun`). Whether a shipyard actually *stocks* a given ship also depends on its production modules: shipyards build L/XL and wharves S/M, which is base-game behaviour. I did not verify this in data.

## 6. Consumables, software, thrusters

- **Missiles:** the ship macro gives capacity (`<storage missile="6"/>` on the X-wing; the ISD has `missile="0" unit="40"`).
  - Launchers are weapons (`class="missilelauncher"`, for example `weapon_krupx_s_guided_macro` in slots tagged `krupx`).
  - The launcher macro's `<ammunition tags="concl protl ionl carb"/>` picks which missiles it fires; each missile macro has `<missile … tags="protl"/>` (`missile_proton_light_macro`).
- **Drones (units):** capacity comes from macro `<storage unit=…>`. They are drone wares (`group="drones"`; all are base-game, such as `ship_gen_xs_repairdrone_01_a`), and loadouts list them as `<unit macro=… exact=…/>`.
- **Countermeasures and deployables** (flares, mines, satellites, resource probes, nav beacons): capacity is per ship class in `libraries/defaults.xml`. SWI replaces the values: S `countermeasure=8 deployable=5`, M 16/15, L 25/40, XL 30/60. All of these wares are base-game.
- **Software:** the ship macro's `<software>` lists wares with `default="1"` (pre-installed) or `compatible="1"` (optional). For the X-wing, defaults are flight assist mk1, long-range scanner mk1 and object scanner mk1; options are dock mk1/2, long-range scanner mk2, object scanner mk2, targeting mk1, trade mk1.
- **Thrusters:** these are not component slots. The ship macro has `<thruster tags="small"/>`, the thruster component's connection is `tags="thruster small component"`, and loadouts put them under `<virtualmacros>`. Only base `thruster_gen_{s,m,l,xl}_*` exist.

## Open questions raised

1. **Default Loadout semantics:** reimplement or approximate X4's level-based generator (`GenerateShipLoadout2`), or redefine "Default Loadout" for the builder? Most SWI ships have no stored default.
2. **The pipeline must layer base + DLCs + SWI + RSP**, not SWI alone, for thrusters, software, drones, deployables, countermeasures and some missiles. Is RSP "core SWI"? It's in the 8.00 install, so v1 scope should decide.
3. **Version drift:** Egosoft's Breaking Changes lists 9.00/10.00 tag changes (`standard` → `advanced`). The current SWI targets 8.00, but a future SWI port could change matching.
4. **Shipyard stocking rules** (module type vs ship size, faction relations) are only partly in data. How strict should "buildable" be?
5. **Bad hand-authored data:** some SWI loadouts reference slots that don't accept the equipment, and one fits two shields to the same `con_shield_01`. The pipeline needs validation and reporting.
